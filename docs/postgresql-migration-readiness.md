## Implemented compatibility

Existing JPA entities use IDENTITY keys, exact BigDecimal amounts, DECIMAL(19,2),
group/user foreign keys and explicit transaction boundaries. Repositories use
JPQL/derived queries rather than MySQL-native repository queries. Mutations lock
the group or user row; password reset consumes its token and increments the JWT
version atomically. These business rules were retained.

Added PostgreSQL JDBC and Flyway database modules. Existing `db/migration/V1–V10`
files remain byte-for-byte unchanged. PostgreSQL has its own `db/postgresql`
location with translated V1–V10 and additive PostgreSQL-only V11. Never point
MySQL at this location or PostgreSQL at the MySQL location.

- AUTO_INCREMENT becomes BIGINT GENERATED BY DEFAULT AS IDENTITY. Explicit old
  IDs are imported; sequences preserve both MAX(id)+1 and the source's next
  AUTO_INCREMENT high-water mark, including gaps/deletions.
- LONGTEXT becomes TEXT; entity JDBC mapping uses portable LONGVARCHAR. Currency
  stays CHAR(3), with its JDBC CHAR type explicit. No floating-point money.
- InnoDB clauses are removed; inline indexes become standalone CREATE INDEX.
  PK/unique/FK/CHECK constraints and cascade rules remain enforced during import.
- Legacy MySQL TIMESTAMP is read in a UTC session. LocalDateTime columns become
  timestamp(6) without time zone containing UTC; invitation entity Instant fields
  become timestamp(6) with time zone. DATE remains a calendar date. UTC is set on
  JDBC connections and Hibernate; timestamp canonical hashes include microseconds.
- Dashboard uses PostgreSQL EXTRACT(EPOCH FROM created_at AT TIME ZONE 'UTC') only
  under the PostgreSQL profile. MySQL retains UNIX_TIMESTAMP.
- Notification pagination omits its cursor predicate when absent, avoiding an
  untyped PostgreSQL null parameter. Recipient authorization remains unchanged.
- Email columns use an ICU nondeterministic primary-strength collation for
  case/accent-insensitive ownership and uniqueness. V11 applies that collation to
  settlement UUID request IDs too: case changes must not bypass duplicate payment
  protection. V11 is exclusively PostgreSQL and does not change MySQL history.
  ICU availability/version and unusual Unicode equivalences must be checked on
  the selected managed target; this is not proof of all MySQL UCA equivalences.

Complexity: moderate schema/configuration and data-transfer work, limited Java
changes; no financial algorithm rewrite and no frontend/API contract changes.
Concurrency, collation, UTC handling, identity floors and Flyway lineage are the
parts requiring explicit target verification.

## Recovery restrictions

Prefer a compatible forward fix. After PostgreSQL accepts writes, switching back
to the stale MySQL V7 database would lose financial changes and may resurrect
revoked JWTs. NEVER roll back to V7 after token-version rollout. Preserve every
user's auth_token_version monotonically, including resets performed after cutover.
Do not restore an older user/token snapshot and reopen authentication. If any
data recovery is required, keep writes/authentication gated until token-version
and record reconciliation is complete; any separate forced reauthentication plan
requires approval. Do not rotate production credentials as an automatic fallback.

Before target writes open, an aborted cutover can leave the frozen source as the
data authority, but restarting service still requires an explicitly approved
authentication-compatible release/recovery plan. After writes open, reverse data
and token-version synchronization is NOT implemented or approved. A failure means
maintenance and forward recovery, not an automatic DB_URL switch. Restoring a
target backup must be rehearsed before relying on it; Free provider snapshots
alone are not proof of a restorable independent backup.
